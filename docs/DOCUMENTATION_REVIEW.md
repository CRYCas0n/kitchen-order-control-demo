## Обнаруженные расхождения и пробелы

1. **25/31 против 39 тестов.** В EMPLOYER/DASHBOARD оставались прежние числа; обновлены. В TEST_RESULTS результаты прошлых этапов сохранены и явно обозначены как исторические.
2. **Противоречивый повторный монтаж.** Старый DEMO сначала предлагал дополнительный КФ-2603, затем отмечал его приёмку. Новый сценарий однозначно разделяет доступное задание и сохранённый результат; reset production не предлагается как обычная подготовка.
3. **Checklist.** Бот показывает несколько пунктов, но подтверждает их одной кнопкой. Документация не обещает независимые отметки каждого пункта.
4. **Обновление сайта.** Изменение в Telegram не вызывает автоматического fetch; нужен «Обновить». Карточка берётся из снимка, не отдельным GET при каждом открытии.
5. **Координатор.** Адресат Telegram — один глобальный ID, а не имя координатора заказа; обычное уведомление не содержит прямой ссылки на заказ. Выполнение/принятие не создают coordinator notification.
6. **Назначение.** Доступ к задачам связан role+assignee_code, не FK на Telegram ID и не уникальным отображаемым именем. Несколько аккаунтов могут разделять код.
7. **Нереализованные действия.** В старых кратких описаниях не хватало явного перечня: нет решения проблемы, согласования переноса, закрытия приёмки, создания следующей задачи и назначения нового срока автоматически.
8. **Seed и production.** Новый seed имеет 2 открытые проблемы; production после настоящих сообщений — 4. API-примеры обозначены как seed, а наблюдения сервера датированы. Seed не создаёт пользователей, reset сохраняет allowlist, но удаляет историю updates/outbox.
9. **Deployment и backup.** push заменяет серверный .env локальным, не делает backup БД/кода, распаковывает до тестов и не обновляет уже существующий Caddy host. Эти свойства теперь указаны отдельно от безопасной последовательности оператора.
10. **Служебные scripts.** public_check меняет настоящую сумму и оставляет аудит; check_lifecycle останавливает сервис. Два screenshot scripts привязаны к Windows Chrome. Они не объявлены универсальными read-only проверками.
11. **Отсутствие CLI disable-user.** В Operations дан ограниченный параметризованный SQL и указано, что отдельной команды/экрана нет.
12. **Границы доказательств.** Прежний живой E2E, fake transport, getWebhookInfo, чистая установка и полное аварийное восстановление — разные проверки. Непроведённые сценарии не называются PASS.

Новых подтверждённых дефектов runtime во время этого этапа не исправляли; изменения касаются документации и её проверочного script. Реальные исторические проблемы в ISSUE_LOG не удалены.

## Проверка документов

Команда: `python -m scripts.docs_check`. Отчёт записывается в [documentation-review.json](../artifacts/documentation-review.json). Проверяются внутренние файловые ссылки, синтаксис JSON и встроенных Python-примеров, присутствие существующих routes/table/env/service значений, безопасный CLI --help и примеры API на временной БД с отключённой отправкой Telegram.

Фактический результат: **PASS**, 26 Markdown-файлов, 9 маршрутов, 8 таблиц, 8 переменных окружения. Summary/history свежего seed совпали с JSON-примерами; проверены admin rework, health, отсутствующий/некорректный order ID и повтор ignored update. Число 39 unittest сверено по исходникам, прежние полные прогоны сохранены отдельно; эта проверка их не подменяет. Первый запуск обнаружил отсутствовавший ещё файл собственного отчёта; после его создания повторная проверка ссылок прошла. Список ошибок итогового отчёта пуст.

Скан перед commit: `python -m scripts.security_check`, затем diff/index review. Он не выводит реальные значения секретов. Процедуры restore/reset/production deploy не запускались ради проверки документации. Внешние ссылки не считаются проверенными только из-за их наличия.

Скан рабочих файлов, индекса и достижимой Git-истории выполнен: **PASS**, findings пуст. Проверяется совпадение с известными локальными credentials и шаблонами token/key; это не доказательство отсутствия любой возможной чувствительной информации.
