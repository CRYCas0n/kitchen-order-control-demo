## Модель данных

`orders` — заказ и бизнес-состояния; `tasks` — действия назначенного исполнителя; `costs` — одна запись план/факт; `history` — человекочитаемый аудит; `telegram_users` — allowlist и роли; `telegram_sessions` — состояние многошагового диалога; `telegram_updates` — уникальные входящие update_id; `telegram_outbox` — результаты и очередь исходящих сообщений.

Foreign keys включаются для каждого соединения. SQLite использует WAL и busy timeout 10 секунд. Транзакция сообщения включает deduplication, изменение данных и создание исходящих сообщений. Сетевой вызов Telegram выполняется вне блокировки SQLite.

Публичные ответы не содержат user ID, bot token, внутренних путей, исходных Telegram payload, photo file_id и паролей. Имена в истории — вымышленные отображаемые имена. Денежная валидация и расчёты используют Decimal; SQLite NUMERIC хранит суммы, возвращаемые JSON как числа. Ограничения схемы запрещают отрицательные/нечисловые расходы и несуществующие связи.

## Развёртывание

Существующий Caddy работает в контейнере. Loopback хоста для него недоступен, поэтому выбран внутренний bridge, аналогично уже установленному LeadRadar. Backend не слушает публичный IP; доверие к proxy headers ограничено текущим IP Caddy `172.18.0.3`. После пересоздания контейнера этот адрес надо перепроверить.

Перед изменением Caddyfile прочитан целиком и сохранён отдельный файл `Caddyfile.before-kitchen-*`. Добавлен один новый блок, `caddy validate` прошёл, затем выполнен reload. Существующие virtual hosts оставлены без изменений. Снаружи после reload портфолио, Playlens, LeadRadar и n8n отвечали HTTP 200.

Сервис непривилегированный, с `ProtectSystem=strict`, `ProtectHome=true`, `NoNewPrivileges=true`, записью только в каталог data и лимитом памяти 220 МБ. Код и `.env` не доступны ему для изменения. Автозапуск включён. Stop/start/restart и сохранность SQLite проверены; весь VPS не перезагружался.

## Честные ограничения

- Нет ровно-однократной гарантии физической доставки `sendMessage` при сетевом разрыве после отправки: Telegram не поддерживает клиентский idempotency key. Неоднозначный результат сохраняется как `uncertain`, без автоматического повтора.
- У прототипа нет фонового повторного назначения/эскалации, ручного закрытия проблем или официального согласования срока. Координатор получает следующее действие и может изменить стоимость переделки.
- Публичный dashboard допускается только для вымышленных данных.
- Автотесты Telegram используют тестовый transport. Они не заменяют живую проверку с пользовательским аккаунтом.
- Технический hostname зависит от стороннего DNS-сервиса sslip.io. Домен не покупался; гарантии доступности внешнего DNS не предполагаются.
