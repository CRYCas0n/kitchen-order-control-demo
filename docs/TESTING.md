# Проверка проекта

Здесь описаны способы проверки. Фактически исполненные прогоны и ограничения находятся в [TEST_RESULTS.md](TEST_RESULTS.md). Наличие теста в исходниках само по себе не означает PASS в новой среде.

## Automated tests

Из корня проекта после установки lock-файла:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Windows:

```powershell
.venv\Scripts\python -m unittest discover -s tests -v
```

Текущий набор содержит 39 методов unittest. В tests/test_app.py: FinancialTests (6) и AppTests (28); в tests/test_dashboard.py: DashboardTests (5). Тестовый transport FakeTelegram заменяет исходящий Telegram API; бизнес-логика, FastAPI handlers и SQLite настоящие. Данные создаются во временных каталогах. Отдельный запущенный Uvicorn для unittest не нужен.

| Группа | Что проверяет |
|---|---|
| Финансы | Контрольные суммы, изменение переделки, NULL/0, нулевая выручка, доход/процент |
| Сроки | DEMO_DATE, перенос без изменения обещания/прогноза, completed_date и исключение активной просрочки |
| Dashboard | Пересекающиеся KPI, непересекающиеся графики, среднее, полные данные, top-5, invalid rows |
| Telegram | Проблема/перенос/выполнение, checklist/photo file_id, роли, владение, повторная проверка назначения/стадии |
| Идемпотентность | Повтор update, четыре конкурентных одинаковых update, rollback до commit |
| Диалоги / доставка | Restart, stale nonce, cancel, неизвестный/отключённый пользователь, uncertain без повтора, transport exception |
| API / безопасность | Basic Auth, HTTPS, CSRF headers/origin, input validation, большие ID, private files, cache |
| SQLite / seed | FK/CHECK/UNIQUE, повтор seed, отсутствие будущего завершения в новом seed |

Предупреждение Starlette об устаревающем httpx TestClient transport отдельно от исходящего HTTPX приложения; последняя проверенная связка проходит. Не меняйте lock-файл только ради сокрытия предупреждения без проверки совместимости.

## Браузерные scripts и их влияние

Установите дополнительные инструменты после runtime-зависимостей:

```powershell
.venv\Scripts\python -m pip install -r requirements-dev.txt
.venv\Scripts\python -m scripts.browser_check
.venv\Scripts\python -m scripts.dashboard_check
```

| Script | Среда | Изменяет данные? |
|---|---|---|
| scripts.browser_check | Временная локальная БД, Uvicorn 127.0.0.1:18888, Chrome | Только временные fixture/HTTP данные, без Telegram |
| scripts.dashboard_check | PUBLIC_BASE_URL из .env, настоящий браузер | Нет бизнес-записей; API/network abort только в браузере |
| scripts.public_check | Публичный сайт, настоящая Basic Auth | **Да:** меняет переделку КФ-2601 на 85 000, возвращает исходную сумму, обе записи остаются в истории |
| scripts.test_report | unittest и снимок HTML-отчёта | Нет production бизнес-записей; перезаписывает локальные artifacts отчёта |
| deploy/check_lifecycle.py | Конкретный VPS | **Да:** stop/start/restart сервиса; не запускайте как пассивную диагностику |

browser_check и dashboard_check используют установленный Windows Chrome при его наличии, иначе Playwright Chromium. Для fallback: `python -m playwright install chromium`. public_check и test_report имеют фиксированный Windows-путь Chrome; на другой ОС перед запуском нужно адаптировать executable_path, одного скачивания Chromium этим двум scripts недостаточно. Эти инструменты не входят в runtime сервера.

Скрипты сохраняют реальные screenshots/JSON в artifacts. Перезапись отчётов не означает новый Telegram E2E. Не запускайте public_check для read-only проверки: используйте dashboard_check.

## Ручной Telegram E2E

Нужны два настоящих Telegram-аккаунта с `/start`: назначенный исполнитель и активный глобальный coordinator. Токен, secret, webhook и сервис должны работать. Используйте согласованный учебный заказ с доступной задачей, не сбрасывайте production seed.

1. Исполнитель: `/tasks` → заказ → «Есть проблема» → новый различимый текст → помощь → подтверждение.
2. Убедитесь, что ответ говорит о сохранении; отдельно проверьте сообщение на аккаунте координатора.
3. На сайте нажмите «Обновить»: проблема, следующее действие, история source=telegram должны совпасть с вводом.
4. Администратор при необходимости сверяет outbox notification=1/status=sent и системную историю. API-подтверждение отправки без проверки второго аккаунта не является доказательством получения человеком.
5. Для монтажа: «Выполнено» → общая кнопка checklist → комментарий → фото либо skip → confirm.
6. На сайте должна быть «Приёмка», completed_date=null, задача completed; открытая проблема остаётся.
7. Для замера на отдельном доступном заказе ожидается «Проектирование».

Фотография в настоящем Telegram-клиенте и сохранение её file_id — отдельная проверка; тестовый file_id этого не доказывает. Новые действия меняют реальную demo БД и не должны маскироваться как чтение.

## Duplicate update

Основная воспроизводимая проверка — test_problem_transaction_duplicate_and_notification и test_concurrent_duplicate_is_one_operation. Ожидание: один бизнес-переход, одно бизнес-событие с данным update_id, одно coordinator-сообщение; остальные ответы duplicate=true.

Для диагностического replay на production допустим только **уже подтверждённо обработанный** update_id, найденный оператором в БД; secret держите вне логов. Сравните историю, задачу и outbox до/после. Не придумывайте новые ID настоящего бота: можно заранее занять будущий update. Самый безопасный эксперимент — изолированная test SQLite и fake transport.

## Admin / rework

Запишите исходную фактическую сумму и доход. Войдите в admin, выберите нужный заказ, замените rework на известную сумму. При полном факте увеличение расхода на X должно уменьшить доход на X. Проверьте новое значение через API/карточку и source=admin в истории. Обновите главную для пересчёта сводки. Верните исходную сумму, если так согласован сценарий; аудит не удаляется.

Проверьте 0 отдельно от пустого поля; неотрицательность, копейки, запрет bool/NaN/Infinity/extra JSON в API; сеть после POST может оборваться уже после commit. UI должен предложить проверить результат, а не заявить однозначную неудачу записи.

## Dashboard и stale data

1. Сверьте все шесть KPI с точными ID заказов по соответствующим backend flags.
2. Нажмите каждый KPI, затем комбинации select-фильтров и reset. Проверьте счётчик доски.
3. Сумма стадий — общее число; сумма сроков плюс invalid_count — общее число; распределение маржинальности — общее число.
4. Проверьте top-5 и приоритет просрочки с проблемой; сводка/attention не должны меняться из-за фильтра доски.
5. На изолированной БД измените stage/forecast/rework, нажмите refresh, сверяйте новые графики и экономику.
6. В DevTools Network временно блокируйте именно `/api/dashboard` либо используйте Playwright route.abort. Старые графики и успешное время должны остаться, предупреждение — появиться.
7. Повторите с malformed HTTP 200, в том числе неверной history при открытой карточке. После снятия блокировки refresh должен восстановиться.
8. Проверьте 1440, 1100, 768 и 390 px; допустим внутренний скролл доски/таблицы, не всей страницы. Числа и подписи должны читаться без опоры только на цвет.

## Production и восстановление

Read-only порядок — health, страница, dashboard_check, telegram-info, outbox, integrity_check. После отдельного разрешённого restart проверяют сохранность известных заказов/истории/диалогов. Backup должен иметь integrity_check=ok; полное восстановление и host reboot нельзя считать проверенными только по наличию команды в инструкции.

В последнем ревью восстановление **чистой установки** проверялось в новом временном каталоге/venv по lock-файлу. Это отличается от восстановления production backup после аварии.

## Фиксация результатов

Для каждого прогона укажите дату, commit/среду, что действительно выполнялось, ожидаемый и фактический результат, источник доказательства. Используйте PASS, FAIL, NOT TESTED. Сохраните честные ограничения: fake transport, прежний живой Telegram, непроверенный реальный reboot/фото. Скриншот из HTML не заменяет пользовательский Telegram-клиент.

Скан секретов: `python -m scripts.security_check`. Проверка документации: `python -m scripts.docs_check` (без production-мутаций). Результаты сверяйте с [TEST_RESULTS.md](TEST_RESULTS.md), изменения поведения — с [ISSUE_LOG.md](ISSUE_LOG.md).
