# Границы текущего прототипа

Это существующие ограничения кода, а не список обещанных доработок. Дата описания — 30.09.2026.

## Предметная область

- 24 вымышленных заказа и фиксированная DEMO_DATE=2026-09-30. Сроки не начинают автоматически считаться от нового календарного дня.
- Все десять стадий отображаются, но через приложение реализованы только переходы после замера и монтажа. Нет drag-and-drop, произвольного редактирования стадии или закрытия приёмки.
- Нет UI/API создания и назначения заказов/заданий, смены прогнозов, согласования версий проекта, кабинетов клиентов и дилеров. Project version — строка для показа, не история файлов.
- Запрос переноса только сохраняется и уведомляет; нет одобрения/отклонения. Предложенная дата проверяется как календарная, но не обязана быть позже текущего срока.
- У заказа одна текущая проблема, новые сообщения заменяют её поля; предыдущие остаются в истории. Действия закрытия проблемы нет.
- Выполнение меняет stage_executor на координатора и текст следующего действия; следующий срок не назначается заново, новая задача не создаётся.

## Доступ и Telegram

- Заказы читаются публично. Это неприемлемо для реальных клиентских/коммерческих данных без отдельного решения доступа.
- Есть allowlist Telegram, но нет полноценной регистрации/управления сотрудниками в UI. Права основаны на role+assignee_code; одинаковый код/роль у нескольких аккаунтов означает общий набор задач.
- Basic Auth admin — один набор credentials; нет отдельных web-аккаунтов, MFA, logout, session management и персонального имени в admin-аудите.
- Один глобальный Telegram-координатор. Поле coordinator в заказе не маршрутизирует сообщение; выполнение/принятие не уведомляют координатора автоматически.
- Checklist подтверждается одной общей кнопкой. Фото только при выполнении, сохраняется file_id; нет загрузки файла на сервер, просмотра фото на сайте и пересылки координатору.
- Нет группового бота, polling Telegram и эскалаций по расписанию. Незавершённые диалоги старше 24 часов отклоняются при следующем вводе, не удаляются отдельным scheduler.
- Защита повторов относится к одному update_id. Telegram API не даёт прикладному коду гарантии «ровно одна доставка» при сетевом обрыве; failed/uncertain не повторяются автоматически. Нет общей команды безопасного resend.

## Экономика и интерфейс

- Admin редактирует только rework_actual. Нет CRUD всех расходов, загрузки оплат, счетов, НДС, себестоимости складских остатков, бухгалтерии или чистой прибыли.
- Отсутствующий факт не заменяется планом. Из-за этого неполные заказы исключаются из экономических сумм; общая выручка сводки не является суммой всех введённых выручек без условий.
- Средняя маржинальность — среднее процентов карточек, не взвешенное по выручке. Низкий процент определяется до округления; показанное 15,00% на границе может иметь low_margin=true.
- Нет realtime, автообновления по таймеру, server-side поиска/пагинации и персональных настроек dashboard. Браузер получает все заказы, историю и задачи.
- Invalid row помечается и защитно исключается из ряда показателей, поэтому KPI при ошибках данных не заменяют контроль invalid_count.
- Offline-имитация — один заранее рассчитанный сценарий заказа 1; это не полноценный offline backend.

## Эксплуатация

- Один процесс Uvicorn и SQLite на одном VPS. Нет репликации, высокой доступности, распределённых workers, нагрузочных гарантий и автоматического масштабирования.
- Схема создаётся через CREATE IF NOT EXISTS; нет framework миграций. Изменение структуры существующей базы требует отдельного решения.
- Доставка архивом не атомарна; код распаковывается до серверных тестов, автоматического rollback всего приложения нет. Скрипты привязаны к текущим host/bridge/Caddy.
- Нет scheduler backup, шифрования/offsite retention, центрального мониторинга, health-алертов, CI pipeline и встроенного rate limiting.
- DNS/HTTPS зависят от внешнего sslip.io и текущего Caddy. Фиксированный proxy IP необходимо сверять после изменения Docker-сети.
- История, updates и outbox не очищаются автоматически. Объём SQLite и backup контролирует оператор.
- Некоторые вспомогательные browser/report scripts требуют Windows Chrome; переносимость runtime не означает переносимость каждого служебного screenshot-скрипта без настройки.

## Границы подтверждённых проверок

39 автоматических тестов и браузерные сценарии выполнены. Прежний реальный Telegram E2E подтверждён отдельно. Новый клиентский прогон после финальных исправлений не выполнен по выбору владельца; сохранённые события и webhook сверены. Реальный reboot VPS, настоящее фото из Telegram и полное восстановление production backup после аварии не заявляются как проверенные.
