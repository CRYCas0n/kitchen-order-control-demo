# Обзор проекта

Состояние описано по коду и доступному серверу на 30.09.2026. Отправная версия приложения — `2d5ae5c`. Документация описывает существующий прототип, а не будущую CRM.

## Назначение

«Контроль заказов кухонной фабрики» помогает координатору видеть, на какой стадии находится кухня, кому поручено следующее действие, где возникла проблема и как переделки влияют на экономику. Это демонстрация для компании, которая продаёт кухни через собственные шоурумы и дилеров, организует производство, замер и монтаж. Конкретная действующая фабрика и её реальные клиенты в проект не заведены.

Вместо разрозненных сообщений исполнитель передаёт проблему через Telegram. Система сохраняет её в заказе и истории, затем пытается отправить уведомление координатору. Руководитель открывает сводку и за несколько секунд видит сроки, проблемы и маржинальный доход.

## Что работает

| Часть | Фактическая возможность |
|---|---|
| Главная страница | Шесть KPI, диаграммы стадий/сроков/маржинальности, экономика, пять заказов внимания и доска |
| Заказы | Чтение карточки, первоначального срока, прогноза, ответственного, следующего действия, задач и истории |
| Фильтры | Стадия, точка продаж, ответственный, наличие проблемы и один выбранный KPI |
| Замерщик / монтажник | Свои задания в Telegram, принятие, проблема, запрос переноса, подтверждение выполнения |
| Координатор | Telegram-уведомления о проблемах и переносах; защищённая форма изменения фактической стоимости переделки |
| Экономика | План и факт; доход, процент маржинальности, неполные данные, низкий процент и убыток |
| Надёжность | Транзакции SQLite, защита от повторного update, сохранённые диалоги и очередь сообщений |
| Имитация | Явно выбранный локальный пример без Telegram и изменения рабочей БД |

Приложение показывает все десять стадий, но не автоматизирует весь производственный процесс. Доска не поддерживает перетаскивание заказов. Реализованы только два перехода после выполнения задания: «Замер → Проектирование» и «Монтаж → Приёмка».

## Основной поток

1. Координатор открывает общую сводку и нужный заказ.
2. Назначенный исполнитель выбирает задание в Telegram и подтверждает проблему.
3. Backend записывает проблему, событие истории и сообщение в очередь одной транзакцией.
4. Фоновая обработка отправляет сообщение настроенному Telegram-координатору; результат доставки фиксируется отдельно.
5. Координатор нажимает **«Обновить»** на сайте и видит запись.
6. В `/admin` он меняет фактическую стоимость переделки; новая сумма заменяет старую, а не прибавляется к ней.
7. Расчёты используют обновлённый факт. При следующем обновлении главной меняется сводка.
8. Монтажник подтверждает checklist, комментарий и выполнение. Заказ переходит в «Приёмку» и остаётся активным.

Сообщение «поставлено в очередь» ещё не означает доставку. Показатель `sent` означает подтверждение Telegram API, а факт получения человеком проверяется отдельно. Сайт не обновляется в реальном времени.

## Как устроено

```text
Браузер → HTTPS / Caddy → FastAPI → SQLite
                    ↘ HTML, CSS, JavaScript → браузер

Telegram → HTTPS webhook → проверка пользователя и задания
         → SQLite: заказ + задание + история + очередь
         → фоновый обработчик → Telegram Bot API → координатор / исполнитель
```

Стек: Python 3.12+, FastAPI, Uvicorn, SQLite и обычные HTML/CSS/JavaScript. Frontend не требует сборки или Node.js. На текущем сервере приложение запускается одним процессом через systemd; Caddy в Docker обеспечивает HTTPS и проксирование. Сам backend не помещён в Docker.

Расчёты выполняет Python, браузер показывает готовые признаки и агрегаты. База находится в `data/app.db` по умолчанию; она не включена в Git и не раздаётся через сайт. Бизнес-изменения проходят через Telegram или единственную admin-операцию изменения переделки.

## Данные и экономика

Seed создаёт 24 вымышленных заказа, три шоурума и пять дилерских городов, шесть заданий. Имена сотрудников и клиентов, суммы, адреса городов и версии проектов — учебные. Настоящие аккаунты Telegram подключаются отдельно; тексты, которые человек отправляет боту, действительно сохраняются и могут появиться на публичной странице. Не отправляйте туда реальные персональные данные.

Дата для расчёта активной просрочки фиксирована: **30.09.2026**, даже если календарная дата изменилась. Время событий при этом настоящее, UTC, а браузер показывает его в своём часовом поясе.

Маржинальный доход = выручка минус материалы, изготовление, доставка, монтаж, комиссия, переделки. При выручке 300 000 ₽ и расходах 200 000 ₽ доход составляет 100 000 ₽, маржинальность — 33,33%. Постоянные расходы не распределены: это не чистая прибыль и не бухгалтерский отчёт. При неизвестном расходе итог не подменяется планом или нулём.

## Что не реализовано

Нет кабинета клиента/дилера, регистрации, полноценного управления сотрудниками и назначениями, создания заказов через UI, официального согласования переноса, изменения прогноза через UI, закрытия проблемы или приёмки. Фотография не скачивается и не показывается на сайте: сохраняется только идентификатор Telegram. Нет WebSocket, автоматического обновления страницы и автоматической повторной отправки неудачных/неоднозначных уведомлений.

Публичное чтение подходит только для демонстрационных данных. Подробные границы — [LIMITATIONS.md](LIMITATIONS.md).
