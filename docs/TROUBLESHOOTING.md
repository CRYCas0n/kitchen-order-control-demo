# Диагностика проблем

Сначала выясните, где сбой: браузер → HTTPS/Caddy → Uvicorn → SQLite → Telegram. Команды сервера выполняются из `/opt/kitchen-control`; секреты и сырые Telegram payload в отчёт не копируйте. Найденные ранее реальные причины сохранены в [ISSUE_LOG.md](ISSUE_LOG.md).

## Сайт не открывается

**Симптом:** браузер сообщает об отсутствии соединения или не разрешает имя.

**Возможная причина:** сеть клиента, DNS sslip.io, недоступный VPS либо Caddy.

**Проверка:** с клиентской машины `curl -I https://kitchen.45-67-202-162.sslip.io`; на сервере `docker ps`, `ss -ltn`, `systemctl is-active kitchen-control`. Для DNS — `nslookup kitchen.45-67-202-162.sslip.io`.

**Исправление:** устраните сбой соответствующего слоя. Если внешний DNS недоступен, backend restart не поможет. Не открывайте порт 18080 всему интернету в качестве обхода HTTPS.

## API health не отвечает

**Симптом:** `/api/health` не возвращает status=ok.

**Возможная причина:** сервис остановлен, неверный upstream, отсутствуют права/диск для БД.

**Проверка:** `curl -fsS http://172.18.0.1:18080/api/health`, затем `sudo journalctl -u kitchen-control -n 80 --no-pager`. 503 с database=unavailable отличается от сетевого отказа и 502 proxy.

**Исправление:** при остановленном сервисе сначала устраните причину из journal, затем `sudo systemctl restart kitchen-control`. При 503 проверьте SQLite и права по [OPERATIONS.md](OPERATIONS.md).

## Сайт открывается, но данные не загружаются

**Симптом:** HTML есть, появляется «Не удалось получить данные».

**Возможная причина:** `/api/dashboard` недоступен или прислал неправильную структуру; браузер использует несовместимые static после неполного обновления; включён offline-сервер с рабочим режимом.

**Проверка:** `curl -fsS https://kitchen.45-67-202-162.sslip.io/api/dashboard`; DevTools → Network → запрос dashboard, его статус; Console — ошибки JS. Не вставляйте в отчёт Authorization headers.

**Исправление:** восстановите согласованную версию backend/static, обновите страницу. На `scripts.offline` вручную выберите имитацию; реального API там нет. Не подменяйте сбой рабочего API учебными данными без явной маркировки.

## Данные на сайте старые

**Симптом:** проблема/изменённая стоимость не видны или время обновления прежнее.

**Возможная причина:** пользователь ещё не нажал «Обновить», запрос завершился ошибкой, выбран режим имитации или фильтр скрывает заказ.

**Проверка:** источник, время и предупреждение над сводкой; сброс фильтров; GET `/api/orders/ID` для нужного заказа.

**Исправление:** переключите источник осознанно, нажмите «Обновить». Если предупреждение осталось, диагностируйте API. Старое время при отказе — правильная защита; его нельзя вручную обновлять для вида свежести.

## Telegram-бот не отвечает

**Симптом:** нет ответа на `/start` или шаг диалога.

**Возможная причина:** сообщение отправлено в группу; webhook не доставляется; token неверен; worker/outbox имеет failed/uncertain; бот заблокирован человеком.

**Проверка:** личный чат; `sudo -u kitchen-control .venv/bin/python -m scripts.manage telegram-info`; затем `... -m scripts.manage outbox` и journal сервиса. Учитывайте сетевую задержку и последовательную отправку очереди.

**Исправление:** поправьте реальную причину (доступ, token, webhook, сервис). Не повторяйте массово uncertain: ответ мог уже уйти. При отсутствии подтверждения не объявляйте бизнес-операцию успешной без проверки истории.

## Webhook не работает

**Симптом:** pending_update_count растёт, last_error_date установлен либо видны 403/422.

**Возможная причина:** URL/сертификат недоступны; секрет в setWebhook отличается от окружения процесса; JSON неверен; приложение не перезапущено после `.env`.

**Проверка:** `scripts.manage telegram-info`, внешний health и `/telegram/webhook` без секрета. Последний должен давать 403 при POST — это ожидаемая защита, не тест исправности всего диалога.

**Исправление:** согласуйте PUBLIC_BASE_URL и secret, restart только kitchen-control, выполните `scripts.manage webhook` из правильного окружения, повторите getWebhookInfo. Не очищайте pending updates без анализа. GET webhook не является поддерживаемым методом.

## Telegram-пользователь не видит задания

**Симптом:** только ID, пустой список или сообщение координатора.

**Возможная причина:** нет активной записи, не та роль/assignee_code, задания уже completed. Имена в карточках не задают права.

**Проверка:** администратор приватно сверяет telegram_users.role/active/assignee_code и tasks.role/assignee_code/status. `/tasks` координатора не показывает задачи монтажника.

**Исправление:** `scripts.manage add-user YOUR_TELEGRAM_ID installer INSTALL-01 'Учебный монтажник'` либо правильная роль/код; затем `/tasks`. Команда не создаёт задач. Не восстанавливайте целиком production seed ради одной демонстрации; используйте отдельную учебную БД.

## Координатор не получает уведомление

**Симптом:** проблема есть на сайте, сообщения на втором аккаунте нет.

**Возможная причина:** COORDINATOR_TELEGRAM_ID не задан, пользователь не активный coordinator, не нажал `/start`, token/доставка отказали. Имя координатора конкретного заказа не выбирает Telegram-адресата.

**Проверка:** история notification_failed/notification_sent/notification_uncertain и `manage outbox`; приватно сверить глобальный ID и allowlist. sent — подтверждение API, не прочтение человеком.

**Исправление:** подключить аккаунт, исправить настройку, restart. Старые проблемы при этом автоматически не рассылаются. При первом показе проекта такая ситуация действительно возникла; позднее сохранённое уведомление было доставлено отдельно, а новый поток проверен независимо. Не выдавайте ручную доставку за автоматический новый E2E.

## Ошибка прав SQLite

**Симптом:** permission denied, readonly database, unable to open database; health 503 или startup error.

**Возможная причина:** БД скопирована root без нужного владельца; каталог data не writable; DATABASE_PATH вне разрешённого systemd ReadWritePaths; диск заполнен.

**Проверка:** `ls -ld /opt/kitchen-control/data`, `ls -l /opt/kitchen-control/data/app.db*`, `df -h /opt/kitchen-control`, `systemctl cat kitchen-control`. `.env` не печатайте.

**Исправление:** восстановите владельца kitchen-control для подтверждённых файлов БД и режим каталога 750, файла 640; разрешение нужно также для создания WAL/SHM. Не используйте `chmod -R 777`. Новый путь БД согласуйте с unit и backup-процедурами.

## Сервис не запускается

**Симптом:** systemctl показывает failed/restart loop.

**Возможная причина:** отсутствует venv/зависимость, недоступен EnvironmentFile, неверный integer COORDINATOR_TELEGRAM_ID, занят порт, неправильный путь, права или лимит памяти.

**Проверка:** `systemctl status kitchen-control --no-pager`, journal, `systemd-analyze verify /etc/systemd/system/kitchen-control.service`, `ss -ltn`, `free -h`.

**Исправление:** устраните конкретный отказ; зависимости устанавливайте из lock-файла. Если меняли unit, выполните daemon-reload, затем restart. Не отключайте все ограничения systemd без понимания причины.

## Reverse proxy возвращает 502

**Симптом:** Caddy доступен, но сайт/health даёт 502.

**Возможная причина:** backend не слушает 172.18.0.1:18080 или изменена сеть Docker.

**Проверка:** health по внутреннему адресу, `ss -ltn`, состояние контейнера caddy; администратор сверяет network inspect и upstream проекта.

**Исправление:** восстановить сервис или согласовать адрес в unit и Caddy snippet/блоке. При изменении IP Caddy также проверьте forwarded-allow-ips. Перед правкой общего Caddyfile — backup, затем validate и reload. Не заменяйте все чужие virtual hosts.

## HTTPS / сертификат

**Симптом:** браузер не доверяет сертификату, hostname не совпадает или curl сообщает TLS error.

**Возможная причина:** DNS ведёт не на сервер, проблема автоматического получения сертификата, закрыты 80/443, изменился hostname.

**Проверка:** nslookup, `curl -I` без `-k`, конфигурация соответствующего host и диагностические логи Caddy.

**Исправление:** согласуйте DNS/host/доступность портов и механизм Caddy. Не отключайте проверку сертификата у пользователей и не переводите admin на публичный HTTP.

## Admin не принимает credentials

**Симптом:** 401, 403, 503 или повторный запрос пароля.

**Возможная причина:** 401 — неверные данные/кэш Basic Auth; 403 — HTTP вместо HTTPS либо недопустимый write Origin/header; 503 — пустой ADMIN_PASSWORD. Изменённый `.env` ещё не применён.

**Проверка:** статус запроса в Network без публикации headers, действующий URL, источник серверных Settings; окно инкогнито с новой попыткой входа.

**Исправление:** настройте пароль приватно, restart, закройте старое приватное окно. ALLOW_LOCAL_HTTP=true применяйте только на локальном loopback. При «Нет подтверждения от сервера» сначала перечитайте стоимость/историю перед повторным POST.

## Некорректные demo data

**Симптом:** «Ошибка данных», неполный расчёт, странная дата или количество отличается от нового seed.

**Возможная причина:** ручное изменение БД; отсутствующий расход; существующий production уже изменён Telegram/admin; старая ошибка завершённого КФ-2611.

**Проверка:** data_error и missing в API; DATABASE_PATH; сравнение с отдельным свежим seed. NULL само по себе может быть намеренным учебным кейсом (КФ-2607), не повреждением БД.

**Исправление:** восстановите конкретное известное значение после backup, не заполняйте неизвестное нулём. Для точной старой ошибки КФ-2611 существует `scripts.correct_demo_dates`; он откажется при бизнес-истории. Обычный повтор seed не исправляет уже существующие заказы. Reset разрешён только для выбранного disposable demo, см. [DATABASE.md](DATABASE.md).
